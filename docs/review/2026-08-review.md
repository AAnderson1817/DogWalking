# Sanpo — production readiness review

**Date:** 2026-08-13 · **Commit:** `c9fa689` · **Branch:** `main`

Scope: the whole repository — 18 Postgres migrations, 11 edge functions, the React PWA (both
personas), the Indigo Emaki visual system, the four GitHub Actions workflows, the four test
suites, and the specs and runbooks in `docs/`. Method: ten independent specialist reviews
(security, money, reliability, frontend, accessibility, design, strategy, privacy, QA,
maintainability), each then handed to a second adversarial reviewer who re-derived every claim
from the source and confirmed, corrected, downgraded, upgraded or refuted it. Severities in this
document are the verifier's, not the original reviewer's; refuted claims have been removed and
are listed at the end so you can see they were checked.

---

## Verdict

The core of this system is better than its stage suggests, and one part of it is genuinely
excellent: the credit engine. The per-client `SELECT … FOR UPDATE` discipline is real and
consistent, the ledger is append-only with a trigger-maintained running balance that the SQL
smoke suite actually verifies, `fn_apply_invoice_paid` makes payment, rollover and grant one
transaction keyed on the Stripe invoice id, and the per-attempt overage idempotency key with live
PaymentIntent reconciliation is a sophisticated fix most teams get wrong. Two specialists
independently attacked the money hot path and neither could break it. The tenancy layer is
similarly strong: row-level security is enabled *and* forced on every bootstrap table, column
grants make `credit_balance` and vault ciphertext unforgeable from any API token, and migration
0014's tenant-consistency triggers close the "I know your UUID" class of cross-tenant write that
most multi-tenant Supabase apps ship with. The Today screen is the most distinctive artifact in
this product category that any of the ten reviewers had seen.

What disqualifies it from being called production-ready today is not subtle. Client self-booking
— one of the two things the client portal exists for — has never worked: `fn_book_walk` filters
on a column that does not exist and raises a Postgres error on every call, and it shipped because
no test in the repository has ever invoked it. The live-GPS channel that broadcasts a named
person's real-time position outside a customer's home is a public, unauthenticated topic that
anyone holding the (publicly shipped) anon key can both read and write. The vault master key —
the thing standing between a database leak and every door code in the product — exists as exactly
one copy in a GitHub secret with no escrow, no key identifier and therefore no possible rotation.
There is no backup, no restore rehearsal, no rollback, and the production deploy workflow has
never executed. There is no refund or chargeback path of any kind. The flagship Today screen
silently deletes schedule rows past about five walks a day with no scroll, on a product sold to
people who do six to ten. The vault's revealed door code renders at 1.70:1 contrast — legible to
almost nobody, outdoors, on a phone. And the Playwright suite that supposedly guards all of this
runs in no workflow, self-skips where it does run, and is currently red at the smallest viewport
it tests.

Where this actually is: a technically accomplished, single-tenant, founder-operated beta with an
outstanding billing core and an unfinished operational, legal and commercial shell — perhaps 70%
of the way to a product one stranger could safely use, and considerably further from the
multi-operator SaaS the brand and the pitch describe.

## Blockers — fix before any real user touches this

### B1. `fn_book_walk` references a column that does not exist, so every client self-booking fails

**Where:** `supabase/migrations/0013_rereview_fixes.sql:314-315` · caller `app/src/lib/api.ts:162`
from `app/src/screens/Booking.tsx:127` · **Discipline:** security / QA

**What:** The atomic booking function filters `service_types … and active`. `service_types` has no
`active` column — its columns are `id, operator_id, name, duration_minutes, credit_cost,
weekend_surcharge_credits, is_default, created_at, updated_at` (`0002_schema.sql:185-195`). No
later migration adds one; the function is defined exactly once and never redefined. PL/pgSQL
resolves SQL inside a function body at execution time, not at `CREATE`, so this passes `supabase
db push` and passes CI. Every call raises Postgres error 42703 (`undefined_column`), which the
client sees as a generic "booking failed". `Booking.tsx` has no fallback path.

**Why it matters:** Client self-service booking is 100% broken and has never worked in any
environment. It also means the `SECURITY DEFINER` function written specifically to close the
non-atomic-booking race has never once executed, so none of its tenancy assertions (property
belongs to caller, pet belongs to caller, service belongs to operator) have ever run against a
live database. An investor demo of the client portal cannot complete a booking.

**Fix:** New migration replacing `fn_book_walk` with the `and active` predicate dropped (or add
`active bool not null default true` to `service_types` and keep it — pick one deliberately). Then
add a smoke assertion that calls `fn_book_walk` under a client session and asserts the happy path
plus each rejection branch, so the next drift of this kind fails CI rather than a customer.

### B2. The vault master key has one copy, no escrow, no key identifier, and no rotation path

**Where:** `supabase/functions/_lib/crypto.ts:24-58` (blob layout at `:36-39`) ·
`supabase/functions/credential-vault/index.ts:22-30` ·
`docs/dev/production-cutover.md:34-37` · `.github/workflows/deploy-production.yml:121` ·
**Discipline:** reliability (blocker) / security (high) / privacy (high) — three disciplines
converged

**What:** The stored ciphertext is exactly `iv(12) ‖ tag(16) ‖ ct` with no version byte and no key
id, and `importVaultKey` accepts any 32-byte key with no identity check. `access_credentials` has
no `key_id` column. There is no re-encryption routine anywhere in the tree. `VAULT_MASTER_KEY`
lives only as a GitHub environment secret, which cannot be read back; the cutover runbook says so
verbatim — "if it's lost, every stored door code becomes unreadable" — and both deploy workflows
push the secret unconditionally with no compare-and-swap, so ticking `sync_secrets` with a
regenerated or mistyped value silently orphans every existing blob. `credential-vault/index.ts:68`
throws a generic `decrypt_failed` that cannot distinguish a wrong key from tampering. Encryption
also passes no `additionalData`, so a ciphertext is not bound to its row.

**Why it matters:** Two failure modes, both terminal. Key *loss* means every operator phones every
client to re-collect their alarm codes, discovered at a customer's front door. Key *leak* — a CI
log, a mis-scoped environment, a contractor with Actions access — decrypts every home-entry code
in the product at once, with no detection and no remediation. "How do you rotate the vault key"
is on every security questionnaire and every insurance application, and today the answer is "we
cannot". Compounding this, the cutover runbook (`production-cutover.md:34-35`) tells the operator
to generate the key with `select encode(gen_random_bytes(32), 'base64')` **in the Supabase SQL
editor** — inside the very database the key is supposed to be independent of, contradicting
`crypto.ts:3`'s own stated design ("never in the DB") and putting the plaintext key into saved
snippets, results history and potentially statement logs.

**Fix:** Prepend a version/key-id byte to the blob and dispatch on it in `decryptSecret`, so two
keys can coexist — that alone makes rotation possible without touching stored data. Add a
`key_id` column, a service-role re-encryption routine, and a startup canary that decrypts one
known row and refuses to serve on failure, so a wrong-key deploy fails at deploy time rather than
at a client's door. Pass `additionalData: credential_id ‖ operator_id`. Write the key to a second
independent store at generation time. Change the runbook step to `openssl rand -base64 32` on the
operator's own machine and say why. Longer term: per-operator data keys wrapped by the master
(envelope encryption) so one tenant's exposure is not all of them.

### B3. No backup, no rehearsed restore, no rollback — and a production deploy path that has never run

**Where:** `.github/workflows/deploy-production.yml` (0 runs, confirmed via the Actions API) ·
`supabase/migrations/` (18 files, no down migrations) · `docs/` (zero occurrences of "restore",
"rollback", "PITR" or "incident") · **Discipline:** reliability

**What:** Eighteen append-only migrations with no reverse path; no point-in-time recovery on the
current stack; no rehearsed restore; and a production workflow that has genuinely never executed,
so the first `0001 → 0018` push against a fresh project will be against live customer data. The
disaster-recovery posture is one line in `production-cutover.md:177-178` noting that Supabase Pro
does daily backups. `migrate` and `deploy-functions` are separate jobs, so a mid-way function
failure leaves new schema against a mixed function set; `sync-secrets` declares `needs: migrate`
rather than `needs: deploy-functions`, so on the runbook's prescribed first deploy the secrets
push races the function deploy and a function can be live before `VAULT_MASTER_KEY` exists.

**Why it matters:** `credit_ledger` and `payments` are the authoritative record of money owed and
money taken. A daily backup means a bad migration at 4pm costs a full day of walk debits, cycle
grants and overage charges, reconcilable against Stripe only by hand. Separately, walk photos have
no backup at any tier and `walk_photos` carries no checksum or size column, so a database restore
rolls the metadata back while the objects do not — post-restore reconciliation is impossible even
in principle, and the photo report is the evidence you would submit in a chargeback.

**Fix:** Turn on PITR before the first paying client. Add a pre-migration step that triggers an
on-demand backup via the management API and fails the deploy if it does not complete. Merge
`migrate` and `deploy-functions` into one job and make `sync-secrets` a dependency of
`deploy-functions`. Rehearse a restore against a scratch project and write it up as
`docs/dev/disaster-recovery.md` with measured RTO/RPO (how long recovery takes, and how much data
you lose). Mirror both storage buckets to independent object storage and record an object checksum
on `walk_photos`.

### B4. No refund, dispute or chargeback handling exists anywhere in the system

**Where:** `supabase/functions/stripe-webhook/handler.ts:104-282` (six event arms) ·
`docs/dev/production-cutover.md:76-80` · `app/src/screens/BillingConsole.tsx:212` ·
**Discipline:** money

**What:** The webhook subscribes to and handles exactly six events. There is no handler for
`charge.refunded`, `charge.dispute.created`, `charge.dispute.closed`, `credit_note.created` or
`invoice.voided`. `payment_status` includes `'refunded'` (`0001_extensions_enums.sql:22`), the
Money screen offers a "Refunded" filter and `status-treatment.ts` styles it — and no code path in
the repository ever writes that value. Concretely: a refund issued from the Stripe dashboard (the
only way to issue one) returns the money but leaves the `payments` row reading `succeeded` **and
leaves the cycle grant in the ledger**, so the client keeps credits they were refunded for. A
client disputing an overage causes Stripe to pull the funds plus the dispute fee, and Sanpo shows
the walk as paid forever with no notification to the operator.

**Why it matters:** Refunds and chargebacks are not edge cases in a consumer services business
taking off-session card charges — they are weekly. The operator's books diverge from Stripe's from
the first refund, the credit balance stays inflated after money is returned, and the operator
learns about a dispute only if they happen to read Stripe's email. This is also the reverse gear
for every other money defect in this document: with no way to unwind a charge, each of them is
permanent.

**Fix:** Subscribe to `charge.refunded`, `charge.dispute.created`, `charge.dispute.funds_withdrawn`,
`credit_note.created` and `invoice.voided`. Add `fn_reverse_payment(p_payment, p_amount, p_reason)`
— `SECURITY DEFINER`, per-client row lock — that flips the payments row to `refunded` and, for
credit-funded reversals, inserts a compensating ledger entry. Add an operator-facing "Refund this
walk" action calling `stripe.refunds.create`, and a dispute strip on the Money screen.

### B5. No Stripe Connect — every operator's client revenue lands in one platform bank account

**Where:** `supabase/functions/_lib/stripe.ts:6-13` · `supabase/functions/create-checkout/index.ts:38-72`
· `docs/dev/production-cutover.md:56,66-82` · **Discipline:** strategy (blocker) / money (high)

**What:** `stripeClient()` reads a single `STRIPE_SECRET_KEY` with no `stripeAccount` option. A
grep across the whole tree for `stripeAccount|application_fee|transfer_data|on_behalf_of|acct_`
returns zero payments-related hits. `operators` has no `stripe_account_id` column. Customers,
subscriptions and off-session PaymentIntents are all created on the platform account. The cutover
runbook confirms the intent: step 4.1 has the founder verify "the bank account payouts land in".

**Why it matters:** Every client payment for every operator lands in the platform's Stripe balance,
and there is no code path that ever moves money to an operator. That is collecting funds on behalf
of third parties, which Stripe requires Connect for and which is money transmission in most US
states. Operator #2 has no way to get paid, so the "sellable as vertical micro-SaaS" line in the
brief cannot be exercised at all.

**Severity note — the two verifiers split on this.** The strategy verifier confirmed blocker. The
money verifier downgraded it to high on the grounds that `docs/spec/00-master-brief.md:4` states
"Operator #1 is the founder (pre-launch)", making a single-account setup the deliberate v1
posture — the founder can ship and collect on it today. Both are right about different questions:
it is not a blocker for *you* going live, and it is an absolute blocker for a second operator and
for the multi-operator investment narrative. Treat it as a blocker on the business plan, not on
the founder's own launch.

**Fix:** Stripe Connect Express or Standard: `operators.stripe_account_id`, every customer /
subscription / PaymentIntent / portal call routed with `{ stripeAccount }`, `application_fee_percent`
on the subscription for the platform's take, Connect webhooks alongside the account-level ones,
and webhook dispatch reading `event.account` to resolve the operator. Budget a multi-week edge-layer
rewrite; the schema is already multi-tenant so the database is not the problem. (Note: Stripe event
ids are globally unique across connected accounts, so the `stripe_events` claim ledger does not
need account scoping.)

### B6. A new operator cannot configure the product — there is no settings surface at all

**Where:** `app/src/lib/api.ts:109-116` (only `select` on `service_types` and `plans`) ·
`app/src/App.tsx:53-76` (no settings route) · `app/src/lib/api.ts:461` (`updateOperator` defined,
zero importers) · **Discipline:** strategy

**What:** `/onboard` collects business name, display name and phone. Two service types are
trigger-seeded by `fn_seed_operator_defaults` (`0002_schema.sql:210-214`: "Private walk 30" and
"Private walk 60"), and zero plans. There is no UI to create a plan, set `credits_per_cycle`,
`price_pence`, `overage_rate_pence`, `rollover_policy` or `stripe_price_id`; no UI to create or
rename a service type or set `weekend_surcharge_credits`; and no settings screen, so
`business_name`, `timezone` and `low_credit_threshold` are unchangeable after signup. The database
is ready — `0004_security.sql:232-249` already grants full CRUD on both tables with correct
`operator_id` policies, and `updateOperator` is already written — this is purely a missing UI.

**Why it matters:** With no plan, `clients.plan_id` stays null, `fn_debit_walk` marks every walk
as overage at zero balance, and `_lib/overage.ts:163` returns `failWithoutAttempt("no plan on
file")` — which inserts a **failed payment row and fires a `payment_failed` notification to the pet
owner for every single walk**. So the un-configured state is not merely inert, it actively duns
your customers' customers. The activation path for a paying operator is: founder logs into Stripe,
creates a Product and Price, then inserts a `plans` row against production Postgres. That is a
consulting engagement, not a product, and it makes a free-trial funnel impossible.

**Fix:** Ship a Settings area: service-type CRUD, plan CRUD that creates the Stripe Price via an
edge function rather than asking for a pasted `price_…`, and operator profile fields wired to the
already-written `updateOperator`. Launch gate: a stranger signs up and takes their first payment
without you touching anything.

### B7. The vault renders a client's door code at 1.70:1 contrast, with a 1.00:1 Copy button

**Where:** `app/src/components/VaultFlows.tsx:152-176` (panel `:158-159`, code `:164`, Copy
`:167-172`, countdown `:173-175`) · **Discipline:** accessibility

**What:** The revealed-secret panel sets `background: var(--pine-950)` and `color:
var(--teal-live)` — both legacy Trailhead aliases that `tokens.css` now remaps into the Sanpo
palette, resolving to `#0C4774` on `#236F86`. Measured against the live stylesheet: the plaintext
door/alarm code (20px, weight 600 — small text, so WCAG requires 4.5:1) renders at **1.70:1**; the
`{countdown}s` timer at `opacity: 0.7` composites to **1.45:1**; the Copy button is
`variant="accent"`, painted with the *exact same* `#0C4774` as the panel, so its body and border
are **1.00:1** against their own container and only the cream label is visible; and the focus ring
on that button is 1.70:1, failing the 3:1 floor for non-text indicators (SC 1.4.11). This is
production code, reached from `AccessVault.tsx:86` and `ClientDetail.tsx:606`.

**Why it matters:** This is the single most safety-critical string the product ever displays — an
alarm or lockbox code for a stranger's home — shown for 30 seconds, outdoors, in daylight,
one-handed. At 1.70:1 it is unreadable on a phone in sun for anyone, disabled or not. The operator
misreads a digit, fails entry, and phones the client for the code, which defeats the vault's
entire reason to exist. It is also the first thing an investor sees in a demo of the flagship
security feature.

**Fix:** Stop routing the vault panel through legacy aliases: `background:
var(--sanpo-color-brand-indigo); color: var(--sanpo-color-brand-cream)` (verified 9.03:1), drop
the `opacity: 0.7` on the countdown, change Copy to `variant="ghost"` (cream fill, indigo border),
and scope `--sanpo-color-border-focus` to yamabuki on the panel so the ring clears 3:1. Then
delete the `--pine-*` / `--teal-*` / `--mist` / `--amber` aliases from `tokens.css` and fix the
remaining call sites (see M-token-drift).

### B8. Today silently deletes schedule rows past about five walks, and cannot scroll

**Where:** `app/src/styles/components.css:704-731` (`.today-emaki` `aspect-ratio: 875/1798` +
`overflow: hidden`), `:746-748` (`min-height: 100dvh` fill) · data source
`app/src/screens/Dashboard.tsx:114-137` · **Discipline:** design

**What:** The schedule is absolutely positioned at `top: 86cqw` inside a fixed-ratio box that is
`overflow: hidden`, and `Dashboard` passes every one of today's walks in unbounded — no slice, no
scroller. Measured at 390×844 by cloning rows in the live DOM: 6 rows puts the last row 40px
behind the nav; 8 rows puts one row entirely below the viewport; 12 rows loses five rows
completely. In every case `document.documentElement.scrollHeight === window.innerHeight`, so
there is no scroll to recover them. The rows remain in the DOM and reachable by screen reader and
Tab — they are invisible on screen only. `docs/spec/07` line 41 explicitly *permits* the
component to scroll vertically, so `overflow: hidden` is not a defended design decision; it
contradicts the spec that governs the component.

**Why it matters:** The target customer is an independent walker doing six to ten visits a day. On
a normal Tuesday their afternoon vanishes from the screen the whole product is organised around,
with no scrollbar, no fade and no cue that anything is missing. This is a scheduling tool losing
appointments.

**Fix:** Stop treating the artwork box as the layout box. Make `.today-emaki` a `min-height`
field: keep the backdrop `position: absolute; inset: 0` behind a normally-flowing column, drop
`overflow: hidden`, and add `padding-bottom: calc(72px + env(safe-area-inset-bottom))` so the last
row clears the nav (this also fixes H-today-viewports and M-nav-overprint). Add Playwright cases
at 8 and 12 visits — and note that the suite guarding this screen does not currently run and is
already red (H-no-behavioural-coverage).

## High severity

### H1. The live-GPS Realtime channel is a public topic — readable *and writable* by anyone

**Where:** `app/src/hooks/useWalkChannel.ts:83` · `supabase/functions/_lib/broadcast.ts:18` ·
zero `realtime.messages` policies in any of the 18 migrations · **Discipline:** security /
privacy / frontend — three disciplines converged (severities high, high, medium)

**What:** the channel is created as `supabase.channel("walk:" + walkId)` with no options, so `private` defaults
to false; the server-side broadcast helper sets `private: false` explicitly. Supabase applies
authorization only to *private* channels. There is no `realtime.messages` RLS policy anywhere, and
`docs/spec/03-security-model.md` never mentions Realtime at all — this is an omission, not a
documented accepted risk. The durable rows are correctly protected
(`walk_gps_points_client_select`, `0004_security.sql:309-312`), which is precisely why the live
stream that bypasses them was missed.

**Why it matters:** While a walk is in progress the operator's device broadcasts each GPS fix to a
topic that any holder of the anon key — which is compiled into the shipped frontend bundle — can
join, from any origin, with no account. That is the real-time position of a named person standing
at a named residential address. The write side is worse than the read side: the same topic accepts
`send`, and `WalkDetail.tsx:64-67` merges `livePoints` straight into the client's map and refetches
on an `ended` event, so the proof-of-service the product sells can be fabricated or terminated by a
third party. The mitigating factor is that topics are not enumerable — an attacker needs a specific
walk UUID — but a UUID is not an authorization control; it leaks through logs, support tickets,
screenshots and shared links.

**Fix:** Pass `{ config: { private: true } }` on both subscribe and broadcast, enable Realtime
Authorization on the project, and add a migration with `realtime.messages` policies scoping topic
`walk:{id}` to the walk's `operator_id` (send + receive) and `client_id` (receive only), mirroring
`walk_gps_points`. Add a test that a foreign token joining the topic is rejected. Record the
Realtime authorization matrix in `docs/spec/03` alongside the table matrix — its absence there is
why this was never built. Per `CLAUDE.md` this touches tenancy and needs owner sign-off.

### H2. Vault re-auth is defeatable by a session-only attacker, and the auth hardening that would fix it is never deployed

**Where:** `supabase/functions/credential-vault/handler.ts:75-84` · `supabase/config.toml:182,185,228,271-276,302-304`
· `app/src/lib/supabase.ts:7` · **Discipline:** security

**What:** Every vault action requires the operator's password, verified server-side, and nothing
else — no AAL2 (authenticator assurance level 2, i.e. a second factor) is ever read; `grep -rn
"aal"` returns nothing in the repository. An attacker holding only a live session (stolen phone,
XSS, exfiltrated localStorage token) can call `supabase.auth.updateUser({ password })` with *no
knowledge of the current password*, then immediately satisfy the vault check with the password
they just set. `secure_password_change = false`, session timebox and inactivity timeout are both
commented out, TOTP enrolment is disabled, the password floor is 6 characters and
`password_requirements` is empty.

The structural half: **`supabase/config.toml` is never applied to any deployed project.**
`deploy-staging.yml` runs `link` / `db push` / `functions deploy` / `secrets set`;
`deploy-production.yml` runs `link` / `db push` / `functions deploy`. Neither runs `supabase config
push`, and that string appears nowhere in `.github/` or `docs/dev/`. Every auth decision in that
file — signup policy, password rules, session lifetime, MFA, OTP expiry, rate limits — governs
`supabase start` on a laptop and nothing else. Staging and production run whatever is set in the
Supabase dashboard, which no file records, no test asserts and no reviewer can see. **The actual
auth posture of the deployed systems is unknown from this repository.**

**Why it matters:** The product's differentiator is an audited vault of door codes, lockbox
combinations and alarm sequences for other people's homes. This reduces "compromise of one browser
session" to "every entry code for every one of that operator's clients, plus a clean audit trail
attributing the reads to the operator". Insurable-loss territory, and a deal-blocker on any
security questionnaire.

**Fix:** Change the settings in the Supabase **dashboard** for staging and production, mirror them
in `config.toml`, and add `supabase config push` to both deploy workflows so the file stops being
fiction (or, if the settings are deliberately dashboard-managed, record the intended production
values in `docs/dev/` and add a staging-smoke assertion that reads them back through the
Management API). Then make the vault require AAL2 rather than a password: enable TOTP and assert
the token's `aal` claim in `credential-vault`. Note that MFA requires the Supabase Pro plan, so
this is partly a billing decision, not just a config edit.

### H3. The vault protects the door code and leaves the key — and its audit trail cannot answer the question it exists to answer

**Where:** `app/src/components/VaultFlows.tsx:141`, `:306-312` · `supabase/migrations/0004_security.sql:172-177`,
`0012_qc_fixes.sql:123` · only audit insert at `0003_credit_engine.sql:489` ·
`supabase/functions/credential-vault/index.ts:92-128` · `0016_vault_rate_limit.sql:38-40` ·
**Discipline:** privacy (high) / security (medium for the audit half)

**What:** Two related gaps in the flagship feature.

*The hint is not protected.* `key_location_hint` is an ordinary column with SELECT, UPDATE and
(after `0012`) INSERT granted to `authenticated`, rendered inline in the credential list with no
re-auth, no audit row and no rate limit. Its placeholder text is verbatim `"Left of the porch,
behind the planter"` — the field actively coaches a means of entry into an unencrypted column.
`properties.address_line1/city/postcode` sits beside it, equally ungated. A single
`GET /rest/v1/properties` plus `GET /rest/v1/access_credentials` with a borrowed session returns,
for every client: full residential address, entry method, and where the key is hidden. For a
`key_on_file` or `lockbox` client, AES-GCM is protecting the less useful half of the secret.

*The log records one event out of four.* `credential_access_log` is written in exactly one place,
inside `fn_read_credential` on a successful reveal. Creating, rotating and revoking a credential
write no audit row; a failed re-auth writes nothing. `accessed_by` is provably always identical to
`operator_id` (the function rejects any other case), so it carries zero information. There is no
IP, user agent, device or walk reference — the only IP ever captured lives in
`vault_rate_limit_attempts` and is deleted by the next attempt past the 60-second window. Unlike
`credit_ledger`, the log has no `BEFORE UPDATE OR DELETE` block trigger. The client — the person
whose door it is — has no read path to it at all.

**Why it matters:** In the scenario the product implicitly promises to handle — a client is
burgled and the walker is a suspect — the log shows "opened 14:02, purpose 'pre-walk entry'",
where the purpose was typed by the suspect. It exonerates nobody and convicts nobody. When a
client asks "who changed my garage code on the 14th, and who still has the old one", the system
cannot answer: a rotation leaves only `rotated_at`, overwritten by the next rotation. Note the
audit scope is *by spec* (`docs/spec/03:56`, `docs/spec/04:33-34`), so this is a product decision
to revisit rather than an implementation slip — but it is the wrong decision for a product whose
trust mechanism is the audit trail, and it is what an insurance underwriter examines hardest.

**Fix:** Either encrypt `key_location_hint` through the same vault path, or drop the field and
force that content into the encrypted secret; change the placeholder to something that cannot be a
means of entry. Add `fn_write_credential` / `fn_revoke_credential` definer functions that perform
the write and insert a log row in the same transaction, with a typed `action` column

### H12. The client's card is charged off-session for a walk they were never quoted and are never told about

**Where:** `app/src/screens/Booking.tsx:91`, `:247-261` · `supabase/functions/complete-walk/handler.ts:114-125`,

### H13. A permanent Stripe failure is classified as transient — the charge is abandoned, and END WALK can wedge forever

**Where:** `supabase/functions/_lib/overage_deps.ts:79`, `:132-140` ·
`supabase/functions/_lib/overage.ts:186-199`, `:202-211` · `app/src/screens/BillingConsole.tsx:131`
· **Discipline:** money (two findings, merged — the second was missed by the original reviewer and
added at high by the verifier)

**What:** `chargeOverageForWalk` inserts a `pending` payments row to claim the walk *before*
calling Stripe. `isCardError` matches only `StripeCardError` and a fixed list of decline codes, so
anything else — including the plain `Error("no payment method on file")` thrown when the customer
has no card attached, and any Stripe `InvalidRequestError` such as an amount below the $0.50
minimum (which `overage_rate_pence check (>= 0)` permits) — falls into the "infrastructure error"
branch and is rethrown. The guard above only checks that `stripe_customer_id` is non-null, and
`create-checkout` persists that id at customer creation, *before* any card is captured. The
consequence is bimodal:

- **Retry within the 10-minute claim lease** (the natural human response to a failed END WALK):
  `getLiveOveragePayment` returns the id-less pending claim, the reconcile branch is skipped, and
  the code returns `already_charged: true` — so the walk is marked **completed** with
  `payment_status: 'pending'` and the charge is silently abandoned. Nothing ever revisits it; the
  only retry affordance in the product is gated on `status === "failed"`, so a `pending` row renders
  no button, and it blocks any new claim forever.
- **Retry after the lease:** the same permanent error throws again, complete-walk 500s forever, and
  the operator sees only "complete-walk failed". The walk can never be completed; the only escape is
  to no-show it from the Calendar and lose the report.

**Why it matters:** This is inside the hot path that otherwise survived attack, and it needs no
infrastructure failure — a client who removed their card in the Stripe portal is enough. A solo
operator standing at a client's door cannot end the walk, with no message explaining why, and the
client's route and photos are stranded in an `in_progress` walk. In the other branch, a $22 charge
becomes permanently uncollected revenue that shows as "Processing" indefinitely with no action
available and no sweeper to find it.

**Fix:** Split the error taxonomy three ways instead of two: *card* errors (mark the claim failed,
notify, re-chargeable — as today); *permanent* non-card errors (no payment method, invalid amount,
customer deleted — mark the claim failed with the reason, notify the operator, and let complete-walk
succeed with `payment_status: 'failed'` so the debt is visible and retryable); and genuinely
*transient* errors (keep the pending claim and rethrow). Replace the bare throw at
`overage_deps.ts:79` with a typed permanent error and treat `StripeInvalidRequestError` as
permanent. Add `check (overage_rate_pence = 0 or overage_rate_pence >= 50)` with 0 meaning "never
charge overage". Show the retry affordance for `pending` overage rows older than the lease, and add
a sweep on the existing daily cron that re-invokes `chargeOverageForWalk` for stale pending claims
— it is already safe to call, since it reuses the same claim and idempotency key.

### H20. The two hardest-to-verify security guarantees have no tests at all

**Where:** `supabase/tests/smoke.sql:11`, `:791` and `supabase/tests/materializer.sql:5`, `:235`
(one transaction per file) · `supabase/migrations/0004_security.sql:410-427`,

(see M-lock-order — that case fails today). Add a storage block to `smoke.sql`: as client A, assert

no seat count, no pricing page and no landing page — `index.html` is a bare SPA shell and `/` is the
operator dashboard behind `RequireRole`. The only Stripe money movement in the codebase is
operator → client, never platform → operator. And the obvious mitigation is unavailable: Supabase's
signup switch is global, and `ClaimInvite.tsx:83` calls `supabase.auth.signUp`, so disabling
operator self-signup also breaks every client's ability to claim an invite.

**Why it matters:** With no billing plumbing, no trial mechanics and no place to state a price, you
cannot run a single acquisition experiment. Meanwhile production fills with unmonetized tenants
storing real people's home-entry codes, and you cannot turn it off.

**Fix:** Move the client claim path off public `signUp` (an edge-function-issued invite) so the
global signup toggle becomes usable; then `shouldCreateUser: false` on the OTP path plus an explicit,
gated operator signup route; an operator-side Stripe subscription with a trial gate in `RequireRole`;
and a public page that states the price.

### H32. The claimed differentiator is already shipped by the market leader, and the billing model this market actually uses is impossible here

**Where:** `docs/spec/00-master-brief.md:6` · `supabase/functions/_lib/overage.ts:163-164` ·
`docs/spec/02-credit-engine.md:36` · **Discipline:** strategy

**What:** Time To Pet already sells Packages: prepaid bundles at a discount or flat rate, drawn down
as booked, with same-day/week/month limits and remaining-visit reporting. That is substantially the
credit mechanic. Sanpo's real delta is narrower than "native subscription/credit billing" implies —
it is subscription-*granted* recurring credits with rollover. Meanwhile the inverse case is not
merely unsupported but actively harmful: a client with no plan hits `failWithoutAttempt("no plan on
file")`, which inserts a failed payment row and fires `payment_failed` notifications to both the pet
owner and the operator, **for every single walk**. There is no one-off payment-mode checkout either,
despite `payment_type` already including `'topup'`, so cash top-ups are collected out-of-band and
entered by hand.

**Why it matters:** Adopting Sanpo requires an operator to move 100% of their existing book onto a
recurring card subscription on day one. Renegotiating payment terms with every client you have is the
hardest sell in small-business software, and here it is a precondition rather than an upsell — while
the differentiator that justifies the ask is not unique enough to carry it.

**Fix:** Make pay-per-visit first-class: a client with no plan gets charged the service type's cash
price off-session at completion — the off-session PaymentIntent machinery already exists, it just
needs a price source other than `plan.overage_rate_pence`. Add a payment-mode checkout for top-ups so
`payments.type='topup'` stops being a dead enum value. Then reposition to "memberships for pet care"
with a retention or cash-flow proof point from real operators.

### H33. There is no two-way messaging — and a complete messaging UI is sitting in the repository unused

**Where:** no `messages` / `conversations` / `threads` table in any of the 18 migrations ·
`supabase/migrations/0001_extensions_enums.sql:45-48` (six system notification types) ·
`app/src/components/InboxField.tsx` (170 lines, tested, styled, reachable only from the DEV-gated
`/dev/inbox`) · **Discipline:** strategy (high) / maintainability (low, for the dead code)

**What:** The only operator↔client communication is one-directional system notifications plus a
`walks.notes` field written at completion. A client cannot ask "can you bring the mail in tomorrow?"
and cannot reply to a report card; the operator cannot reach a client from inside the app.
Meanwhile `InboxField` is a full correspondence surface — thread list, search, unread counts,
mobile index/thread split, compose and send — with typed models, its own unit test counted in the 93,
and ~212 lines of `components.css`. There is no table, no `api.ts` function and no production route.
The JS is correctly stripped from the production bundle; the CSS is not, because CSS is not
tree-shaken.

**Why it matters:** In-app client communication is table stakes in this category and is consistently
what pet-sitting operators cite as why they stay on a platform. Without it, every real conversation
happens over SMS, the operator's phone stays the system of record, and the "visit archive" lock-in
layer is worth much less because the context lives elsewhere. The good news is that the UI is
already built against infrastructure that already exists.

**Fix:** A `messages` table scoped by `operator_id` + `client_id`, Realtime-subscribed (privately —
see H1), optionally threaded to a walk, delivered through the existing notification bell. Roughly a
week. Then wire `InboxField` to it. If messaging is *not* the next thing you build, move
`InboxField` and its CSS into a clearly marked `src/prototypes/` directory and say so in
`app/README.md`, so a maintainer does not spend an afternoon tracing where messages come from.

### H34. The domain model is one visit on one date — no overnights, boarding or house-sitting

**Where:** `supabase/migrations/0002_schema.sql:260-284` (`walks`: `scheduled_date date` +
`window_start` / `window_end time`, no end date) · `0001_extensions_enums.sql:9-11` (`walk_status`)
· `0003_credit_engine.sql:108-134` (`fn_walk_cost` prices off the ISO day-of-week) ·
**Discipline:** strategy

**What:** There is no way to express a span of days at all: no multi-day state in `walk_status`, no
per-night rate, no holiday premium (only `weekend_surcharge_credits`), no drop-in series tied to a
vacation. The weekend surcharge is computed from a single `scheduled_date`, which is meaningless for
a stay. (Twice-daily visits *are* possible — the unique index is on `(schedule_id, scheduled_date)`,
so two recurring schedules per client work fine.)

**Why it matters:** For most solo pet-care professionals, holiday and vacation sitting is the
highest-margin revenue of the year. A product that cannot book Thanksgiving overnights forces a
second system for the most profitable work — and whichever system holds the profitable work wins the
subscription. Note this is consistent with `docs/spec/00`, which scopes the target to dog walking;
the mismatch is between that scope and the "pet-care operations SaaS" positioning in `CLAUDE.md` and
the brand.

**Fix:** Generalise to `starts_at` / `ends_at timestamptz` plus a service category, or add a `stays`
parent owning child visits. Do it before the credit engine ossifies around per-walk debits — pricing
an overnight as N credits is fine, but the schema has to express the span first.

## Medium severity

**M1. `send-notification` verifies the caller is *an* operator but never that the notification is theirs.** `index.ts:27` discards `requireOperator`'s return and fetches the notification through the service-role client by id alone, so any registered operator (signup is open) can force an email to another tenant's client, and the four differentiated responses form an existence-and-type oracle. Bounded only by UUID unguessability, which is not an authorization control. Every other edge function gets this right, which makes it a one-off omission. Add `.eq("operator_id", operator.id)`, return a neutral 404 for both cases, and add an `emailed_at` send-once guard. *(security medium / privacy low / QA low.)*

**M2. A magic-link operator can never use the vault, and each attempt burns a rate-limit slot.** `SignIn.tsx:42` creates passwordless accounts and no operator path ever sets a password, while `credential-vault/handler.ts` gates every action on `verifyPassword` — and calls `allowAttempt` *before* the check, so five tries lock them out. The error reads "password verification failed", which sounds like a typo rather than "your account has no password", and `verifyPassword` collapses every GoTrue error to a boolean so the distinction is discarded. A paying operator is permanently locked out of the flagship feature on a client's porch, and support cannot fix it in-product. Return a distinct `password_not_set` code with an inline set-a-password flow, and do not count it against the limit.

**M3. The "Needs attention" total can never clear, and the recovery workflow lies about collecting money.** `invoice.payment_failed` inserts a failed row on *every* Stripe retry and nothing resolves them when the invoice finally pays, while `MoneyValueRail.tsx:5-7` sums every failed row ever written, unbounded — one $90 invoice that dunned three times leaves $270 in "Needs attention" beside $90 in "Collected". A stale failed overage row also keeps rendering "Retry charge"; clicking it finds the succeeded row, returns `already_charged`, and `BillingConsole.tsx:94` reports "Recovered $22.00" for a charge it did not make. `listPaymentsDetailed` has no limit or date filter, so past PostgREST's 1000-row default all three headline numbers silently under-report. Mark superseded rows resolved, bound the rail to a period, and hide the retry button when a succeeded row exists.

**M4. Production deploys have no repeatable post-deploy verification.** `deploy-production.yml` ends at `deploy-functions` and asserts nothing — not that the functions boot, not that a service invocation returns 200 — while the throwaway staging environment has three checks. A function failing at import time deploys "successfully" and 500s on first call. `production-cutover.md` §9 is a genuine nine-step verification but covers the first cutover once and is never run again. Mitigated by production deploys being manual and approval-gated. Parameterise `staging-smoke.yml` by environment and chain a read-only subset against a reserved fixture tenant.

**M5. CI validates migrations against a hand-written shim, never against `supabase db push`.** `shim.sql:82-91` creates `storage.objects` as a plain table owned by the migration role, so storage policies always apply in CI regardless of real ownership, and `db-reset.sh:32` is a bare `psql -f` loop that never exercises migration bookkeeping or per-file transaction semantics. Green CI therefore does not predict a successful deploy, and the first full `0001 → 0018` push against a fresh project has never been performed. The runbook's "must be owner of table objects" recovery loops (0004/0008 use bare `create policy`) and may itself be stale. Add a nightly scratch-project `db push` from zero, and guard the storage-policy blocks with `drop policy if exists`.

**M6. The service worker is a 3.0 MB atomic precache with no update path and no tests** — four disciplines converged. The `.js` glob sweeps in the code-split mapbox chunk (1,798,215 of 3,034,367 bytes, 59%), which a token-less deployment downloads on every deploy and never executes; `cache.addAll` is all-or-nothing, so one failed asset voids the install *and* skips `skipWaiting`; registration has no `update()`, `updatefound` or `controllerchange`, so a resumed PWA can run a weeks-old bundle against evolved edge contracts; `isNeverCache` — the only thing standing between a shared device and a repeat of the worst bug this codebase has had — is verified by nothing; and `stampServiceWorker` swallows all errors, so an unstamped build silently loses the offline shell and permanently disables the cache sweep with a green build. Filter mapbox out and runtime-cache it, use per-URL `add` under `Promise.allSettled`, add an update prompt, extract and unit-test a pure `routeFor(url, method)`, and narrow the stamping catch.

**M7. The GPS outbox silently destroys route data after ~8 minutes while the banner says "CURRENT".** Attempts increment whenever `navigator.onLine` is true — captive portals, one bar with no throughput — so a batch is deleted after 480 s with no log, counter or flag; and there is no outbox-backed indicator at all, since `WalkMode.tsx:374-376` drives its banner purely from `onLine`. Because `drainOnce` returns after the first failure, batches shed one at a time and the route looks plausibly continuous rather than obviously broken. Gate the counter on evidence of real connectivity, raise `maxAttempts`, flag the walk when a batch is dropped so the report says so, and surface real outbox depth.

**M8. Sign-out leaves the previous account's GPS batches and walk snapshot on the device.** `signOut` clears the session and three pieces of React state and nothing else. Worse than it looks: the outbox is constructed only inside Walk Mode, so after sign-out no drain loop exists and the raw coordinates sit indefinitely — until the *next* operator on that device opens Walk Mode, at which point drain attempts to POST them under the new session (the write is correctly refused by RLS, so the points burn attempts and drop). Same shape as the service-worker leak already fixed, in the two persistence layers that never got the same treatment. Delete the database and the `pawtrail:walk:*` keys on sign-out, plus a boot-time ownership check.

**M9. Every list query is unbounded and all filtering happens in the browser.** Across 664 lines and 64 exported functions of `lib/api.ts` there is not one `.limit()` or `.range()`. Today calls `listPayments()` and `listClients()` unfiltered to render at most five failed rows; `PortalHome` pulls every joined walk row ever (~470 for a client three years into a 3×/week plan) to render one card. At v1 scale this is waste rather than breakage, but it degrades quietly with tenure on the screen an operator opens dozens of times a day on cellular. Push filtering server-side and bound every list.

**M10. Nothing on any screen is live, including the elapsed counter on the walk underway.** No `postgres_changes` subscriptions, no polling, no visibility refetch. `Dashboard` has no interval, so *everything* freezes at mount: the counter ("18 min" an hour in), walk statuses, distance, which walk is current, the low-credit and failed-payment strips, and the date — a PWA left open past midnight shows yesterday's walks. The same number ticks correctly in Walk Mode, so the product contradicts itself. `channel.subscribe()` also takes no status callback, so a failed join is mute. Add a 60 s tick, a `visibilitychange` refetch, scoped `postgres_changes`, and a subscribe status callback.

**M11. Calendar drag-to-reschedule uses HTML5 drag-and-drop, which does not fire on touch.** `Calendar.tsx:220-249` has no pointer or touch handlers and no `touch-action`. There is a real fallback (the walk is a button opening an action sheet wired to the same `reschedule()`), but the draggable affordance still renders on a phone, so the phase-06 headline interaction advertises itself and does nothing on the primary device — and Playwright declares only Desktop Chrome, so nothing would catch it. Use Pointer Events, or gate the affordance behind `matchMedia("(pointer: fine)")`.

**M12. No route has a `<main>`, three screens have no `h1`, and every route shares one page title.** Two `<main>` elements exist in the codebase and none in `screens/`; SignIn, NotFound and ClaimInvite have no `h1` (ClaimInvite no heading at all); `document.title` is "Sanpo" everywhere and is never assigned. Screen-reader users navigate unfamiliar apps by landmark and heading, so the only way through Walk Mode or Money is linear Tab from the top. Move one `<main>` into each shell, add the three headings, and add a `useDocumentTitle` hook that also writes to a hidden polite live region.

**M13. The live walk timer and distance have no accessible names.** `WalkMode.tsx:393-399` is two bare `<span>` elements with no label, `aria-label` or `role="timer"`, and no visual label to fall back on — a screen-reader user hears "12:34" and "1.2 km" with nothing saying what they are. Elapsed time is the number deciding whether the 30- or 60-minute service about to be billed was delivered. Separately `LiveWalkBanner.tsx:31` puts the elapsed time inside the link's `aria-label` while a 1 s interval re-renders, so the accessible name changes every second. The codebase has no visually-hidden utility; add one.

**M14. Revealed credentials clear after a fixed 30 s with no warning, no extend, and no spec.** The countdown that would tell you how long is left renders at 1.45:1 (B7), and a timeout forces the whole re-auth + purpose cycle again, writing another audit row — so the trail fills with noise resembling suspicious repeated access. Thirty seconds is tight in gloves at a keypad in the cold and insufficient with a motor or cognitive disability or magnification. The limit appears in no spec, only a code comment citing one that does not mention it. Add an "Extend", announce at 10 s, fix the contrast, and write the rationale into `docs/spec/03`.

**M15. The `prefers-contrast: more` escalation is defeated for 46 secondary-text call sites.** The high-contrast block redefines `--sanpo-color-text-secondary`, but `tokens.css:6,26` bind `--ink-500`/`--ink-700`/`--text-2` directly to `--sanpo-color-neutral-muted`, which the override never touches — emulated in Chromium, `--text-2` and `.section-label` stay `#5D7180` while the role token correctly darkens. That covers 39 inline styles plus `.section-label` app-wide, including the failing calendar label from H24. This is the mitigation the other two contrast findings lean on, and it reaches about half the surfaces it appears to. Move the escalation onto `--sanpo-color-neutral-muted`, or repoint the aliases.

**M16. `role="tablist"` is applied with no tabpanels, no `aria-controls` and no arrow keys.** Both segmented controls (`Calendar.tsx:127-144`, `ClientDetail.tsx:113-130`) declare tab roles with `aria-selected` over bare `<div>` content, with no roving `tabIndex`, no key handling, and no `aria-label` on ClientDetail's. A screen-reader user is told "tab, 5 of 5, selected" for the operator's main client workspace — whose fifth tab is the vault — reaches for the arrow keys the announcement implies, and nothing happens. Incorrect ARIA is worse than none: either wire the panels properly or use `aria-pressed` buttons.

**M17. The illustration is one 875×1798 master served to every device with no `srcset`.** A 430pt @3× phone requests 1290 device pixels against an 875px plate (47% upscale); even a 390pt phone upscales 34%, so on the phones that decide whether this reads as premium the spire and the dog's fur are visibly soft. Ship a 2× master with `srcset`/`sizes` and precache only the 1× plate, so the offline budget the `perf(today-field)` work reclaimed is unchanged. (The seasonal plate matrix is a costed roadmap item, not a defect — a 2× master alone lands near 1.5 MiB.)

**M18. The client portal is still on the pre-rebrand shell.** `BottomNav.tsx:41` appends `bottom-nav--rail` only for operators, and every Indigo Emaki nav rule is scoped to `[data-navigation-persona="operator"]`, so the client keeps the old opaque bar with the indigo-filled active pill and has no desktop rail at any width; the Today illustration is imported nowhere in the portal. Two visibly different vintages across the two halves of one product — where the client half is what your customers' customers touch and what an investor is shown as "the client experience". Delete the persona fork and apply the operator treatment to both.

**M19. Money's state marks are fallback-font glyphs Nunito does not contain.** `PaymentStatus.tsx` renders `✓ … ! ↩` into bordered boxes; measuring glyph advance widths shows Nunito supplies the ellipsis but **not** ✓ (U+2713) or ↩ (U+21A9), so the two most important marks on the money surface — plus the ✓ beside DONE on Today — are drawn by whatever system font the device has, with synthesised weight. The mark literally looks different on your Mac and the operator's Pixel. Draw the four states plus a real check on the approved 24×24 / 1.75px grid, route through `ApprovedIcon`, and drop the bordered box.

**M20. Desktop is a phone in a cream void.** `.page` caps at 640px, so 1440×900 is an 88px rail, 356px of cream, a 640px column and 356px of cream — 56% of the screen carrying nothing — and `.calendar-week`'s seven columns get about 87px each, so an operator planning next week cannot see next week. The cap is defensible as a reading measure and indefensible for a grid, but it is also spec 05's stated rule, so a `.page--wide` (~1120px) for Calendar, Money and Clients is a spec amendment to make deliberately.

**M21. The type system has no quiet voice.** `body` is weight 600 against a 200–1000 variable axis, and of 76 `font-weight` declarations 26 are 900, 21 are 800, 20 are 700 and only three are 600 — so timestamps, metadata, captions and helper text have nowhere to go and de-emphasis can only be carried by colour, which is the token already under contrast pressure in H24. This is why the non-Today screens read as uniformly loud despite a good palette, and it is the cheapest single improvement available to them. Introduce `--fw-body: 400` / `--fw-emphasis: 700` / `--fw-display: 900` and re-measure contrast on anything that drops.

**M22. `.today-emaki-page { padding: 0 }` removes the nav clearance `.page` provides.** Measured with the standard three-visit fixture: 32px of overprint at 320×568 and 17px at 360×640. Both scroll, unlike the ≥6-visit case, but the screen ships overprinted on load on every 320–360pt Android device — the cheap phones a solo walker is most likely to carry — and it reproduces in a demo with no special data. The B8 restructure should carry the fix.

**M23. There is no data import path, so switching cost runs entirely against you.** No CSV, no bulk create, no batch endpoint; every writer is a single-row insert. A solo professional with 35 clients and 50 pets faces a full unpaid day of data entry to *try* the product, on top of renegotiating billing terms with all of them (H32). This is the mechanical reason a switcher who loves the demo never switches, and it presents as a brutal signup-to-activation ratio that looks like a marketing problem. Build a CSV importer accepting Time To Pet and Precise Petcare exports with a preview-and-map step, paired with concierge migration for the first 50 operators.

**M24. Hard single-operator ceiling with no upgrade path.** `operators.id` is both primary key and the auth user id, `walks` has no assignee, and every RLS policy scopes on `operator_id = auth.uid()`, so a second walker literally shares the owner's login — which also hands them the vault and the billing console — and no record exists of who did which visit, so the vault's audit trail cannot answer "who opened this door". Hiring walker #2 is the natural success event for a growing solo operator and the moment this product must be abandoned, which inverts net revenue retention. Add a `staff` table, `assigned_to` on `walks`, and per-walker vault identity, priced per seat.

**M25. No client intake, lead capture, or signed service agreement.** The only public routes are `/signin`, `/onboard` and `/claim/:token`; there is no request-service form, no inquiry funnel, no client-completed intake, and no agreement, waiver or vet-release record anywhere in the schema or specs. Commercially the operator's website has nowhere to send a prospect. Legally, these businesses handle keys, administer medication and authorise emergency vet care, and storing door codes with no signed agreement between the parties is a gap an acquirer will flag. Add a public per-operator intake URL creating an `invited` client, plus a versioned agreement accepted at claim time.

**M26. The two genuinely differentiated assets do no commercial work.** The vault's encryption, re-auth gate and access log are invisible to the client — the only client-facing mention is one line telling them *not* to enter codes, and `credential_access_log` has exactly one SELECT policy, scoped to the operator — and the Today screen exists nowhere a prospect can reach. "Your door code is encrypted, and here is every time it was opened and why" is a trust story no competitor can tell. Add a client-facing Home Access panel (one new RLS policy plus a screen), a shareable "how your home access is protected" page, and a public Today screen — after H3, since the trail currently records one event in four.

**M27. No push notifications.** The service worker registers `install`, `activate` and `fetch` only — no `push`, no `notificationclick`, no VAPID key, no subscriptions table — and the only out-of-app channel is email, which is env-gated and optional (H17). "Your walker just finished, here are the photos" is the moment that makes a pet owner love the product and it currently arrives as an email or not at all, while `low_credit` and `payment_failed` reach the operator only if they open the app. Add Web Push, fanned out from the database webhook that already drives `send-notification`; note iOS requires home-screen install, which makes the existing prompt load-bearing.

**M28. A walk has no time bound, so it can neither stop recording nor ever finish.** No maximum duration, no server-side auto-complete, no stale sweep, and `complete-walk` is the only exit from `in_progress`. Because the dashboard fetches only today's walks, a walk abandoned yesterday is invisible, never completes, never debits or charges, and never sends a report — silent revenue loss plus an orphaned row, on top of whatever GPS was recorded after the visit ended. Cap the session at `duration_minutes + 30` behind a "still walking?" prompt, sweep `in_progress` walks older than six hours, and surface stale walks regardless of date.

**M29. Notification email goes to unverified addresses with no consent, no unsubscribe and account details in the body.** `clients.email` is operator-typed and never reconciled with the claimant's authenticated address (H4 shows they can differ). The Resend payload carries no headers object, so there is no `List-Unsubscribe` pair — now a hard deliverability requirement at Gmail and Yahoo — and the footer has no unsubscribe link and no postal address, while the `low_credit` body contains the client's balance. One typo in the Roster form sends a stranger a recurring feed of when a named person's house is empty. Reconcile at claim, add per-type opt-outs and a one-click route, add the headers and an address, and link to the portal instead of embedding the balance.

**M30. No security headers on the deployed frontend.** `vercel.json` is a single `rewrites` array — the only deploy config in the tree — and `index.html` has no meta CSP, so there is no CSP, HSTS, `X-Content-Type-Options`, `Referrer-Policy` or `Permissions-Policy` anywhere. The session token lives in localStorage, so one XSS in the dependency tree reads it and then reads every client's address and key-location hint with no further obstacle, which is what makes H3 compound; and a missing `Permissions-Policy` means an injected iframe inherits geolocation on a page whose purpose is precise location. Cheapest item in this document and the first thing a questionnaire scores. (Do not count tightening the wildcard CORS as the fix — these APIs authenticate by bearer header, so CORS is not a control there.)

**M31. RLS has drifted from the schema, and the check that would notice is a hardcoded list.** `0004_security.sql:40-52` is the only place RLS is ever enabled and it iterates a literal array of the 18 tables that existed in 0002; `plan_change_intents` and `vault_rate_limit_attempts` have been added since with neither `enable` nor `force`, relying solely on `revoke all`. `smoke.sql:568-573` re-hardcodes the same array, so the test structurally cannot see them, and no catalog query exists anywhere. No live exposure today — the grants hold and PostgREST cannot reach either table — but a single future blanket grant fails open with nothing to catch it, and invariant 7 has no automated enforcement at all. Enable and force RLS on both, replace both loops with a catalog query minus a written exemption list, and add `security_invoker` to `v_my_operator` plus `set search_path` to the three trigger functions lacking it.

**M32. Lock-order inversion between `fn_debit_walk` and the cancel-refund trigger.** `fn_debit_walk` locks `clients` then `walks`; the BEFORE UPDATE refund trigger runs with the `walks` tuple already locked and then locks `clients` — the inverse. The headline scenario cannot deadlock, because the trigger's lock sits inside an `old.credits_debited > 0` branch a not-yet-debited walk never enters; the reachable cycle is an already-debited walk cancelled at the same moment a *retry* of complete-walk re-enters `fn_debit_walk` between its two lock statements. The outcome is a detected 40P01 abort, not corruption, but it lands on completion with no monitoring, so it presents as an unreproducible "END WALK sometimes fails". Move the refund into an explicit cancel RPC that locks clients first, and write the canonical order into `docs/spec/02`.

**M33. The CI invariant greps are trivially bypassed by whitespace.** Tested empirically: both a multi-line `update clients\n set credit_balance = 0` and an aliased `update clients c set credit_balance = 999` sail through the gate cited in `CLAUDE.md` as enforcement for invariant 1 — and almost every multi-clause UPDATE in this repo is written across lines. A check that cannot fail is worse than no check, because it is listed as evidence of rigour and stops anyone looking harder. The privilege side *is* covered by smoke assertions pinning `insufficient_privilege`, so what the grep uniquely guards is a definer function writing the balance outside the ledger trigger. Replace it with a `pg_get_functiondef` catalogue assertion requiring an allowlist entry and a `for update`.

**M34. Seven negative assertions in `smoke.sql` catch `when others`, and one measures the wrong control.** The suite contains both idioms; the block at `:684-692` is labelled as testing client-booking RLS but inserts a walk whose property belongs to a different client, so the tenant-consistency trigger raises first — RLS is never the control under test, and weakening the policy's `client_id` predicate would not fail this test. The security matrix is the artifact cited as proof of tenant isolation, and one of its cells measures the wrong thing. Convert all seven to the pinned-SQLSTATE idiom and give the booking test a correctly-owned property.

**M35. Four edge functions have no tests, and `change-plan` can silently prorate to zero.** `change-plan`, `create-checkout`, `billing-portal` and `send-notification` have inline logic in `index.ts` with no handler seam, so the Deno suite cannot reach them. The concrete hazard: `change-plan/index.ts:66-71` reads the billing period from the subscription item, falls back to the subscription, then **defaults to `0`** — so a missing period yields `fraction = 0`, the client is prorated to zero credits, and the call returns 200 with no error. Stripe has already moved that field once, which is why both shapes are read; the next move fails silently. Extract a handler with a deps interface, test both period shapes, and make the missing case a 409.

**M36. Distance is miles on Today and kilometres in Walk Mode and the client's report.** `format.ts:131` exposes only `distanceKm(m)`, used by Walk Mode and by `ReportCard` — the report the pet owner receives — while `Dashboard.tsx:110` bypasses the formatter with an inline miles conversion. The token layer stacks three brand generations, ~60% dead, with a raw hex on the billing ledger.** `--orange` resolves to brand *indigo*, as do `--pine-600`, `--pink-ink`, `--mint-ink` and `--lilac-ink`, so a maintainer writing `var(--orange)` in good faith gets blue; nine aliases have zero references. Same defect class as the emaki bug already paid for once. Delete the dead aliases, repoint the survivors, replace the hexes, and add the no-raw-hex CI grep that would give the rule in `CLAUDE.md` teeth.

**M38. 240 inline style objects form a second, untokenized styling system.** Concentrated in `ClientDetail` (29), `Calendar` (20), `WalkMode`/`PortalBilling`/`Booking` (19 each) and `VaultFlows` (18), and mostly reaching for legacy aliases rather than CT-1 roles — all six surviving `var(--mist)` uses are inline, so the alias block cannot be deleted until these move. A design-system change is then a search across a 1816-line stylesheet *and* 240 JSX expressions, which is precisely the change this product will keep making. Promote the recurring patterns in the six heaviest files into named classes, then ban `style={{` outside `components/`.

**M39. `ClientDetail` dead-ends with the wrong diagnosis and no retry.** The QC pass introduced `LoadError` + `loadErrorMessage` (which translates a fetch failure into "You appear to be offline") and applied it to 11 modules; `ClientDetail` — the largest screen and the destination of the Clients tab — uses neither, rendering `EmptyState title="Client not found"` with the raw error as the hint. An operator on a weak connection outside a client's door is told the client does not exist, with no retry and a raw string like "JWT expired". (`Roster` has a retry button; its narrower defect is the untranslated string.) Use `LoadError` with `onRetry`, distinguishing a genuine `PGRST116` from a transport failure.

**M40. `types.ts` is produced by a bespoke script CI never runs and never verifies.** `scripts/gen-types.py` is referenced by no workflow, no npm script and no runbook, yet its 1125-line output is the contract the whole TS-strict frontend checks against. It is currently in sync, so this is latent — but when migration 0019 lands without a regeneration (likely, since most contributors lack the local stack), typecheck passes against a schema that no longer exists and the failure surfaces as a production runtime error. The `database` job already has Postgres, so the fix is two lines: run the generator, then `git diff --exit-code`.

**M41. Six npm advisories, four high, and the fix for the two that matter is a major upgrade.** `react-router-dom` 6.30.4 carries an open-redirect advisory (GHSA-wrjc-x8rr-h8h6) and an SSR-hydration constructor-injection advisory; remediation requires 7.x. The PostCSS path-traversal advisories are dev-only via Vite and can be deferred. The open redirect matters most on the two unauthenticated routes (`/signin`, `/claim/:token`) a phishing link would target. Plan the router 7 migration as its own change with the routing tests it needs.

## What is genuinely strong

This section matters as much as the findings: it is the list of things not to break while fixing
everything above.

**The credit engine is the best thing in this repository.** Every balance mutation happens inside a
`SECURITY DEFINER` function that takes a per-client `SELECT … FOR UPDATE` before reading, and the
discipline is consistent rather than aspirational. `credit_ledger` is append-only with a
trigger-maintained `balance_after` chain ordered by `seq`, blocked from UPDATE and DELETE by
`fn_ledger_block_mutation`, and the smoke suite actually verifies the chain. The
either-fully-credit-funded-or-fully-overage invariant is enforced in one place rather than scattered.
Two specialists attacked this path independently and neither could break it.

**The Stripe integration is more careful than most Series-A billing code.** `fn_apply_invoice_paid`
makes payment, rollover and cycle grant a single transaction keyed on the Stripe invoice id, so a
replayed webhook cannot double-grant. `stripe_events` is a stateful claim ledger with a lease, which
closes the claim-release race that a naive `ON CONFLICT DO NOTHING` leaves open. Overage uses
per-*attempt* idempotency keys with live PaymentIntent reconciliation, so a database failure after a
successful charge cannot produce a double charge — a subtle fix most teams get wrong. Bill-before-
complete ordering is deliberate and correct.

**Financial history cannot be destroyed by an API role.** `authenticated` has no column grant on
`clients.credit_balance`; `credit_ledger` and `payments` are select-only; every client-referencing
foreign key is `on delete restrict`. Invariant 1 is not a convention here, it is a privilege.

**Multi-tenancy is enforced in depth.** Row-level security is enabled *and forced* on all 18
bootstrap tables with a baseline `revoke all`. The operator and client personas share the
`authenticated` role and are separated by policy plus column grants plus per-persona guard triggers —
the correct approach given the constraint. Migration 0014's tenant-consistency triggers close the "I
know your UUID" class of cross-tenant write that most multi-tenant Supabase apps ship with. Every
edge function asserts tenancy except `send-notification` (M1), which makes that one a genuine
omission rather than a pattern.

**The vault's cryptographic core and its privilege model are right, even where its custody is not.**
AES-256-GCM with a per-record IV; `0012_qc_fixes.sql:120-124` genuinely removes the `authenticated`
INSERT path to `ciphertext`, so the ciphertext column is unreachable from any API token; the read
path goes through an audited definer RPC; and the rate limiter was correctly moved from in-memory to
Postgres in 0016. Both storage buckets are created private. All three photo upload paths route
through `compressImage`, whose canvas re-encode strips EXIF — including GPS coordinates — and no edge
function logs PII.

**The service-worker privacy fix holds.** REST, auth, realtime, functions and storage are network-only,
which is what closed the cross-account cache leak, and the reasoning is written into the file. This
is the single most important correction in the project's history and it is intact.

**Release engineering is well above the stage.** Three parallel CI jobs against real Postgres 17
running the actual migrations plus two SQL suites; the deploy gate implemented as a *failing job*
rather than a skipped `if` (a subtle and correct choice); checkouts pinned to the validated
`head_sha`; SHA-pinned actions with a deliberate Node 24 migration already done; environment-scoped
secrets; and a production deploy behind a typed confirmation phrase that refuses unless CI is green
on the exact commit. `staging-smoke.yml` has 27 runs with the last four green and genuinely replays
two user journeys end to end against the real staging project.

**The frontend has real engineering discipline.** TypeScript is genuinely strict —
`noUncheckedIndexedAccess`, `verbatimModuleSyntax`, `erasableSyntaxOnly` — `tsc -b` is clean, and
there are six escape-hatch casts in the whole non-test source. There is not one `supabase.from`
outside `lib/api.ts` and not one `TODO` or `@ts-ignore` in ~11.7k lines. The genuinely tricky async
units were extracted as pure functions and tested properly: `geo.ts`, `gps-batcher.ts`, `map-fit.ts`,
`selectors.ts`, `credits.ts`, `format.ts` (including a spring-forward DST case). The 67-plus Deno
tests are the strongest suite in the repo — `vault_test.ts` covers all six double-charge
reconciliation branches, `webhook_test.ts` pins 21 real behaviours — and `materializer.sql` proves
idempotency and no-resurrection.

**Accessibility has real wins where somebody looked.** All 72 interactive elements measured across
four screens meet the 44px touch-target minimum, with zero SC 2.5.8 violations. `prefers-reduced-motion`
is handled. `prefers-contrast: more` escalation exists and works for the tokens it reaches. The Sheet
focus trap cycles correctly and restores focus to the trigger on both Escape and backdrop click —
re-tested and upheld. Reflow at 320px is clean. `<html lang="en">` is set, and 16 of 20 screens carry
an `h1`.

**The visual system has a genuine point of view.** The Today screen — the day as a single illustrated
scene, the emaki progress stroke, ruled rows instead of the card-grid mush the competition ships — was
described by two independent reviewers as the most distinctive artifact in this product category. The
colour layer under it is unusually well built: real role tokens, `prefers-contrast` escalation, and
measured ratios with the reasoning written into the CSS (even where the measurement method was wrong).
The logo mark — the leash as an S — is good.

**The documentation that exists is honest and useful.** `app/README.md` is a real onboarding document
with architecture notes and recovery playbooks that most seed-stage products never write. The
comments explain *why* rather than restating the code: the `color-mix` `@supports` block, the
network-only rationale, the offline-resume merge. `docs/dev/production-cutover.md` §9 is a genuine
nine-step go-live verification, and §8 already tells the operator to write a privacy notice — the
repo knows what it is missing.

## Product, market and brand

*Written for the founder rather than the engineer.*

### Is the niche real?

Yes, and it is well chosen. Independent pet-care professionals are underserved by software built for
multi-walker agencies, they handle other people's house keys for a living, and they are chronically
bad at billing — which is exactly the wedge a credit/subscription engine addresses. The
solo-first framing is a genuine positioning, not a euphemism for "small".

The problem is that the wedge is narrower than the pitch claims. Time To Pet already sells
**Packages**: prepaid visit bundles at a discount or flat rate, drawn down as booked, with
same-day/week/month limits and remaining-visit reporting. That is substantially the credit mechanic.
Sanpo's genuine delta is *subscription-granted* recurring credits with rollover — memberships rather
than packages. That is a real difference and it is worth something, but it is a narrower claim than
"native subscription/credit billing", and it is not obviously enough to justify the switching cost
you are asking for.

And the switching cost is severe, because it compounds three ways. To adopt Sanpo an operator must
(1) hand-type every client, pet, property, medical note, vet contact, access code and recurring
schedule, because there is no import path of any kind (M23); (2) renegotiate payment terms with
100% of their existing book on day one, because a client with no plan cannot be charged at all — the
system inserts a failed payment and dunning notification for every walk (H32); and (3) accept that
the most profitable work of their year, holiday and vacation overnights, cannot be booked in the
product at all (H34). Each of those alone is survivable. Together they produce a signup-to-activation
ratio that will look like a marketing problem and is actually a product problem.

The most valuable single change on this list, commercially, is making **pay-per-visit first-class**.
The off-session PaymentIntent machinery already exists; it needs a price source other than
`plan.overage_rate_pence`. That converts the pitch from "move your whole book onto subscriptions" to
"start with what you already do, and upgrade the clients who want a membership" — which is a demo
you can actually close.

### Where the differentiation actually is

Not in scheduling, and not in the credit engine. It is in two things you have already built and are
doing nothing commercially with:

**The audited access vault.** AES-256-GCM, column-level privilege revocation, a re-auth gate, an
append-only access log. Nobody in this category tells this story. The pet owner's real fear is
handing their house key to a stranger, and "your door code is encrypted, and here is every time it
was opened and why" is the operator's best closing line with a nervous prospect. Today the client
learns none of it: the only client-facing mention is one line of copy telling them *not* to enter
codes, and the access log has exactly one read policy, scoped to the operator. Surfacing the log in
the client portal costs one RLS policy and one screen (M26). That is the highest-leverage
commercial change in this document. Do it *after* H3, though — the trail currently records one event
out of four and every field in it is self-attested by the person being audited, so showing it to
customers before fixing it would be selling something you cannot back.

**The visual identity.** The Today screen is genuinely distinctive and it lives behind
`RequireRole` with no public equivalent. Put it on a public page. It is the cheapest marketing asset
you own.

### What is missing to be a business rather than a product

Four things, in rough order of how hard they block:

1. **A second operator cannot be paid.** Every client payment for every operator lands in one Stripe
   balance with no code path that moves it out (B5). Until Stripe Connect exists, "vertical SaaS for
   independent pet-care professionals" is a description of an app the founder uses.
2. **A stranger cannot activate.** There is no settings screen at all: plans, prices and service
   types are read-only in the product, so onboarding operator #2 requires someone with Stripe
   dashboard access and psql (B6). That is a consulting engagement, and it caps the business at
   however many operators you can personally hand-hold.
3. **You do not charge anybody.** No operator subscription, no trial clock, no paywall, no pricing
   page, no landing page — and open signup you cannot close without breaking client invites (H31).
   You cannot run a single acquisition experiment from this state.
4. **Your best customers churn by definition.** The schema supports exactly one human per business
   (`operators.id` *is* the auth user id, and `walks` has no assignee). Hiring walker #2 is the
   natural success event for a growing solo operator, and it is the moment this product must be
   abandoned — which inverts net revenue retention and also means the vault's audit log cannot say
   *which person* opened a door (M24).

Two more that will be raised in any diligence conversation: there is no way to delete or export
anyone's data (H5) and no privacy notice, terms, or consent record anywhere in the product (H6), in
a system holding residential addresses, door codes, pet medical records and GPS traces terminating
at people's homes.

### The honest read on the visual system

The Today screen is the real thing — on a phone, with three walks, it is the best-looking screen in
this category by a wide margin, and the decision to render the day as one illustrated scene rather
than a grid of cards is a point of view rather than a skin. The token layer beneath it is unusually
well built for a solo product.

But the vibe exists on exactly one screen, at one viewport, with one data shape, and it breaks in
all three directions. Past about five walks a day the flagship screen silently deletes rows with no
scroll (B8). At 1440×900 the primary action is cut off by the fold and at 768×1024 the navigation
bar physically overprints the schedule text (H27). And everything that is not Today is a competent
but anonymous cream-and-navy form application with a different type scale, a different button shape
and a measurably different cream — #EEE2D4 against a brand cream of #FEF6EA (H29). The client
portal, which is what your customers' customers actually touch, is still on the pre-rebrand shell
entirely (M18).

Right now this is a magazine cover stapled to a spreadsheet. The gap between them is where the
investment-grade impression is being lost, and closing it is mostly cheap work rather than a
redesign: promote the emaki decisions into the token layer, make the Today rows tappable so the
screen is a tool rather than a poster (H30), unfork the portal's navigation styling, and stop
stretching the hero plate (H28). Three of those are hours, not weeks.

Two structural cautions. First, several of the design review's proposed *fixes* — a landscape
desktop composition, a `.page--wide` for Calendar and Money, pill buttons everywhere — contradict the
locked responsive contract in spec 07 and the layout rule in spec 05. Those are owner decisions and
spec amendments, not remediation, and they should be made deliberately in a commit rather than
drifted into. Second, the one automated guard on the "locked" composition does not run in CI and is
currently failing at the smallest viewport it tests (H18). Every claim in the status log that the
composition is protected currently rests on that suite.

## Method and limitations

Ten specialist reviews were run in parallel against `main` at `c9fa689` — security, money,
reliability, frontend, accessibility, design, strategy, privacy, QA, maintainability. Each report
was then handed to a second reviewer in the same discipline whose brief was adversarial: re-derive
every claim from the source, and confirm, correct, downgrade, upgrade or refute it. Verifiers had no
authority to soften a finding without evidence and were explicitly rewarded for finding things the
first reviewer missed — 19 additional findings came out of that pass, including several of the most
serious items in this document (the public Realtime topic, the permanent-Stripe-error END WALK
wedge, the mid-walk photo loss, the never-deployed auth config, the unenforced append-only rule).
The two phases together made 973 tool calls. Every severity in this document is the verifier's.
Where verifiers within different disciplines disagreed, the disagreement is stated in the finding
(B5 is the only case where it changes the headline).

Several findings were verified by more than reading. The accessibility contrast numbers were
re-derived by per-pixel sampling of the rendered backdrop in headless Chromium, not computed from
tokens. The design measurements were taken from the running dev server at ten viewport widths. The
bundle and precache figures were measured byte-exact from the committed `app/dist`. The white-screen
failure was reproduced by serving that build and driving it with a browser. The CI invariant-grep
bypass was reproduced in a scratch tree. Workflow run history and branch protection were queried
from the GitHub API — `deploy-production.yml` has `total_count: 0` runs, and `main` reports
`"protected": false`.

**What could not be checked, and why.** There is no Docker, Supabase CLI, `psql` or Deno in this
environment, so no database was ever executed: every claim about migrations, RLS policies, grants,
guard triggers, definer functions and lock ordering is read from SQL text rather than proven against
a running Postgres. The 67-plus Deno tests were read, not run, and they use mocked dependencies
throughout, so nothing here was verified against a real Stripe payload. There were no Stripe or
Resend credentials, so no webhook, proration, refund or dispute event shape was observed. No
authenticated session could be established, so every screen behind `RequireRole` — the vault, Walk
Mode, Calendar, Roster, Money and the entire client portal — was assessed from source, from the
DEV-gated fixture routes, and (for the vault panel) by injecting its exact markup against the running
stylesheet; nobody ever saw those screens with real data in their real layout. There were no real
devices and no iOS Safari, so the wake-lock, background-geolocation, clipboard-retention, touch-drag,
PWA-install and screen-reader announcement conclusions all rest on documented platform behaviour plus
the confirmed absence of any handling in the code, rather than on observation. And the hosted Supabase
projects could not be inspected at all, which matters more than it sounds: since `config.toml` is
never pushed, **the actual auth configuration, backup posture, log retention and cron state of
staging and production are unknown from this repository** (H2, H15).

**The structural weakness of this review.** This codebase was largely written by Claude, and it has
now been reviewed by Claude — twenty times over, adversarially, but still by the same kind of system
that produced the code. That correlation is real and you should price it in. The practical effect is
asymmetric: findings of the form "here is a defect, at this file and line, with this consequence" are
cheap to check and several were reproduced empirically, so they are trustworthy. Conclusions of the
form "this part is fine" are exactly where a shared blind spot would hide, and they carry much less
weight. Treat the "What is genuinely strong" section as a hypothesis worth an independent human
audit, not as a finding — particularly for the credit engine and the RLS matrix, where two reviewers
declared code correct that neither could execute. The single highest-value thing you could buy right
now is a few days of an independent human payments engineer and an independent human penetration
test against a real staging environment, aimed specifically at the areas this review declared safe.

### Considered and dismissed

These claims were made by a first-pass reviewer and refuted or materially narrowed by the verifier.
They are recorded so you know they were examined rather than missed.

- **"A stale response can bind a credit adjustment or a door code to the wrong client."** Refuted as
  stated. The wrong-client outcome requires `/clients/:id` to change while `ClientDetail` stays
  mounted; all four navigations into that route come from different routes, each of which unmounts
  it, and React discards state updates from a destroyed instance. `AccessVault` loads once with an
  empty dependency array and has no in-screen client picker. Survives only as L10 (Calendar week
  paging, worst outcome a blank week).
- **"Every 5xx across all eleven edge functions is returned with no log line."** Refuted in detail:
  `stripe-webhook` and `send-notification` both log before returning. They are also the two that
  bypass the shared wrapper, which is why H14 stands as a defect in `serveFunction` rather than a
  universal claim.
- **"The `hasPaymentForInvoice` bug affects every plan-change proration and every manual invoice."**
  Refuted. `change-plan` passes `proration_behavior: "create_prorations"`, so proration items ride
  the next cycle invoice, which takes the immune `fn_apply_invoice_paid` path. Retained at low (L5).
- **"The auto-refund trigger lets a delivered walk be refunded, and a re-completed walk be free."**
  The code does both things, but no shipped surface reaches either — the status buttons are gated to
  scheduled/in-progress, the client guard trigger permits only `scheduled → cancelled`, and no
  un-cancel exists. Downgraded to latent (L6).
- **"Mutable prices silently re-price booked walks."** True of the SQL, unreachable in the product:
  there is no pricing UI at all, and `weekend_surcharge_credits` is 0 for every operator. Downgraded
  to L7, with a note that it becomes real the day B6 ships.
- **"No tax handling is a medium risk because operators will sell taxable services."** Downgraded:
  `service_types` has no editor, so the only rows that exist are the two seeded walk types, and dog
  walking is the untaxed case in most states. Retained at L8 for the address-collection half only.
- **"The two RLS-less tables are a live exposure."** Downgraded. Both carry `revoke all … from
  public, anon, authenticated`, PostgREST cannot reach either today, and new entities are not
  auto-exposed. Retained at medium as drift and missing enforcement (M31), not as a leak.
- **"The FK graph makes deletion impossible even for a DBA."** Refuted — `on delete restrict` only
  blocks a naive single-statement delete; deleting children in dependency order works. Also, an
  operator already holds DELETE on `clients` and can remove a childless one today. H5 stands as a
  missing product surface, not an impossible one.
- **"Wildcard CORS on the edge functions is an exfiltration vector."** Refuted. These APIs
  authenticate by `Authorization` bearer header rather than cookies, so a wildcard origin grants an
  attacker page nothing it could not already do with a stolen token. Tighten it as defence in depth,
  but the missing security headers (M30) are the real finding.
- **"The credential audit trail's narrow scope is implementation drift."** Corrected: it is exactly
  what `docs/spec/03:56` and `docs/spec/04:33-34` specify, so it is a product decision to revisit
  (and the spec must change with the code), not a bug. Security downgraded it to medium on those
  grounds; privacy's broader "cannot answer the question" framing is what carries H3.
- **"An END WALK racing a portal cancel can deadlock."** Refuted for that scenario — the trigger's
  `clients` lock sits inside an `old.credits_debited > 0` branch a not-yet-debited walk never enters.
  Retained at medium for the narrower already-debited retry interleaving (M32).
- **"No user journey is tested in CI, ever."** Corrected: `staging-smoke.yml` genuinely replays the
  operator onboard and invite-claim journeys against real staging after every deploy. The claim
  stands for pre-merge coverage and for the money journey, which is what H18 says.
- **"A prop rename between `api.ts` and a screen ships green."** Refuted — `tsc --noEmit` runs in CI
  and types flow from `lib/types.ts`.
- **"The complete messaging UI could be demoed as a shipped feature."** Downgraded to low: the
  JavaScript is correctly stripped from the production bundle by the static `import.meta.env.DEV`
  gate. Only the CSS ships (L21).
- **"Dashboard has no `h1`."** Factually wrong — `TodayIllustratedSchedule.tsx:82` renders one inside
  a labelled section. The landmark finding stands for SignIn, NotFound and ClaimInvite (M12). Two
  further corrections in the same report: the error-span count is 20, not 17, and the mark-read `✓`
  is a 3:1 graphic that passes rather than a 4.5:1 text failure.
- **"Money's state marks read as broken-image placeholders."** Refuted by rendering them at 3× —
  they draw as bordered stamps. The underlying problem turned out to be worse and different: Nunito
  does not contain ✓ or ↩ at all (M19). Also refuted in the same report: "conversation rows have no
  hover" (they do, as do client rows, pet rows and walk cards), and `.today-emaki-page{overflow:
  hidden}` was misattributed as the clip in B8 — the real clip is `.today-emaki`'s fixed-ratio box,
  and the Dashboard's follow-up strips below it are fine.
- **"Sign-out leaves undelivered GPS points that grind through backoff and drop."** Corrected, and
  worse: no drain loop exists at all outside Walk Mode, so the batches sit indefinitely until the
  next operator on that device opens Walk Mode (M8). Walk snapshots, by contrast, *are* cleared on
  successful completion — only abandoned walks leave one.
- **"The operator's pending-GPS indicator clears as if the points had been delivered."** Corrected:
  there is no outbox-backed indicator at all; the banner reads "CURRENT" throughout (M7).
- **PostgREST `db-max-rows` truncation** was raised as a silent-wrong-answer risk for unbounded
  queries. Supabase leaves it unset by default, so today the cost is latency and bandwidth only
  (M9).
- **The Supabase Storage backup policy** underlying part of B3 could not be verified from here — that
  Postgres backups exclude Storage objects is a vendor-policy claim. The in-repo half (no mirror, no
  checksum column, no mention in the cutover checklist) is confirmed.
- **The `supabase db push` "must be owner of table objects" failure** documented in the runbook could
  not be confirmed and may be stale, since the `postgres` role is a member of
  `supabase_storage_admin` on hosted Supabase. Either way M5 stands: CI cannot tell you which is
  true, and that is the finding.
