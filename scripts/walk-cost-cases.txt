# Walk-cost cases: one weekend-surcharge question per line, asked of all
# three implementations by scripts/check-walk-cost-parity.sh.
#
#   weekendWalkCost         app/src/lib/walk-cost.ts     what Booking quotes
#   fn_walk_cost            0043, the live fallback       what fn_debit_walk charges a row with no snapshot
#   fn_snapshot_walk_price  0044, BEFORE INSERT trigger   what every new row is stamped with
#
# Format: <expected>\t<credit_cost>\t<surcharge>\t<scheduled_date>, all
# integers except the ISO date. TypeScript decides the weekday from
# `T12:00:00Z` + getUTCDay (`walk-cost.ts`'s rule, lifted out of `credits.ts`
# by fix(walk-cost)); Postgres reads `isodow` off the DATE. A case cannot see
# a zone, so none of them pins how the leaf parses the date on its own: the
# gate does that by running the TypeScript side under two fixed offsets
# either side of the day boundary — where a leaf reading the LOCAL day at a
# constant offset answers a day out on one side or the other — and under
# America/Chicago and Australia/Sydney, two DST zones whose daylight seasons
# are complementary, where a leaf whose error is DST-dependent passes both
# fixed offsets and answers a day out in whichever zone is on daylight time
# today, on the rows dated in that zone's STANDARD time (each block below
# names its rows). A Sunday read as Saturday is still a weekend, so only a
# Saturday or a Monday can show it.

# ── the week itself ───────────────────────────────────────────────────────
# A Friday is deliberate: `isodow in (5, 6)` — the off-by-one that reads
# "Fri/Sat" for "Sat/Sun" — surcharges it and lets Sunday through, so the
# Friday and the Sunday go red in opposite directions. July is Sydney's
# standard time, so 2026-07-04 (Sat) and 2026-07-06 (Mon) are the two rows
# the Australia/Sydney run answers a day out for a DST-dependent leaf while
# Sydney is on daylight time (October to April; measured, third pass).
1	1	1	2026-07-01
1	1	1	2026-07-03
2	1	1	2026-07-04
2	1	1	2026-07-05
1	1	1	2026-07-06

# ── US daylight-saving transition Sundays (America/Chicago), each with the
# Saturday before it. A DATE has no zone, so DST cannot move its weekday and
# these rows pin nothing on their own (the first version of this file said
# they did — review of PR 2). Of the four, only 2026-03-07 — a Saturday
# dated in Chicago's standard time — is a row the America/Chicago run
# answers a day out for a DST-dependent leaf, and only while Chicago is on
# daylight time (March to November); the Sundays are invisible to that leaf
# and 2026-10-31 is dated in daylight time (the second pass said all four
# were caught; measured otherwise in the third) ─────────────────────────────
2	1	1	2026-03-07
2	1	1	2026-03-08
2	1	1	2026-10-31
2	1	1	2026-11-01

# ── calendar edges: leap day, year boundary (Thu, Fri, Sat). 2027-01-02 is
# the other row the America/Chicago run catches a DST-dependent leaf on ────
1	1	1	2028-02-29
1	1	1	2026-12-31
1	1	1	2027-01-01
2	1	1	2027-01-02

# ── the amounts: a surcharge of 0 on a weekend, and 2 + 3 both ways ────────
1	1	0	2026-07-04
5	2	3	2026-07-05
2	2	3	2026-07-01
